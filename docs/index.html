why two models

Self-review inherits the author's blind spots.

Ask a model to check its own work and it tends to agree with itself. It repeats the assumption that caused the problem, because the assumption is invisible from the inside. Running the critic on a different model family, from a different vendor, gives you a reader that has to reconstruct your intent from the artifact instead of remembering it. It is not a guarantee of catching more — it is a way of not sharing the author's assumptions by default.

So the split is structural, not stylistic. Codex is invoked in a read-only sandbox and cannot edit, stage or commit anything. It reads, it reports, and every fix stays on the Claude side.

One Claude session runs the whole thing — it dispatches the workers, owns every commit, and decides what to do with each review. The pages below call it the coordinator.

Codex can't write

Every Codex call runs in a read-only sandbox. It can read your repository and run git log, and it cannot modify a single byte. There is no mode in which the reviewer edits your code.

Only the coordinator commits

When several implementers work at once they share one working tree, so none of them may touch git. Work is committed at the join, one commit per task, scoped to that task's own files.

Every critic loop ends

A reviewer reading a document again always finds one more thing. Each review stage is capped at two passes, after which the author revises once and the pipeline moves on. The cap, not agreement, is what ends the loop.

Agreement is never proof

Two models liking the same answer is a signal, not a verdict. Nothing is accepted because both agreed; in investigate, a hypothesis is only settled by an observation that could have disproved it.

Findings are recorded with their outcome

Every review finding is logged with what became of it — fixed, kept deliberately, or checked and found false — alongside what the round cost. You can see for yourself whether the second model is earning its time.

What the Claude side can do

Codex being read-only is only half the picture. Claude does write files, run your build and tests, and create commits — on a branch it makes, never on your default branch, and never merging or pushing unless you say so. It refuses to start on a dirty working tree.

No other plugin required

foureyes depends on nothing but Claude Code and the Codex CLI. Install it into any repository and the four commands work on their own.

getting started

What you need.

Requirements

Claude Code, a git repository, and the Codex CLI signed in:

npm install -g @openai/codex
codex login

Without Codex the commands still run if you pass --skip-critics, but only one model family is involved and the cross-checking is gone.

You need an account with each vendor — a Claude Code subscription and a ChatGPT or API account for Codex. Reviewing a pull request additionally needs the GitHub CLI (gh) signed in.

Install and update

/plugin marketplace add Sultan1993/foureyes
/plugin install foureyes@foureyes

To update later:

claude plugin marketplace update foureyes
claude plugin update foureyes@foureyes

Restart Claude Code after updating so the new skills register. To remove it: /plugin uninstall foureyes@foureyes.

Your code goes to two vendors, not one

This is the trade the design makes. Whatever the commands read — source, diffs, commit history — is sent to Anthropic and to OpenAI, each under its own terms and retention policy. If your repository cannot be shared with a second provider, this plugin is not for it, and --skip-critics only avoids that by turning off the thing you installed it for.
